# 0009 Watermarked live admission and deterministic SQL projections

Status: accepted for the implemented live slice

Date: 12 November 2026

The [streaming design](../streaming-design.md) separates durable intake from a live view that can exclude late events. Keep the owner's ten-minute event-time delay and the [authoritative metric definitions](../metrics.md), including separate authorisation decline rate and expiry count.

Validate the complete versioned contract with the same Python decoder as intake **before** exposing event time to Spark. A normal row UDF deliberately avoids additional Pandas/Arrow dependencies. Reject malformed, unsupported, wrong-dataset, inconsistent-hash or out-of-clock input before watermark calculation; intake independently retains its original bytes and reasons. The live query uses `withWatermark(event_time, '10 minutes')` and `dropDuplicatesWithinWatermark(event_id)`, with no additional Spark stateful operator. Its checkpoint, database generation, query role and generated group prefix are distinct from intake. Existing intake markers without a role retain their original intake identity.

The PostgreSQL live sink stores an immutable admitted-event ledger, projections and batch commit in one transaction. Its replay hash covers the admitted semantic event set, since Spark may choose a different physical copy of a duplicate on retry. Database event and payment-sequence uniqueness survive Spark state eviction. Conflicts retain evidence and stop the affected query without overwriting canonical history. Intake can later discover a conflict that live deduplication suppressed; the status check therefore includes durable intake conflicts and canonical-hash agreement.

Batch and streaming share the transition values and sequence-walk SQL under `sql/shared/`. Relative includes are resolved by the CLI SQL reader; the refactor preserves the existing migration's SQL meaning. Batch continues to rebuild by arrival, while live rewalks the entire admitted history of affected payments. SQL holds sequence gaps, excludes illegal transitions and over-refunds, and calculates exact integer money. Each payment must have one merchant/currency identity agreeing with known reference data; inconsistent identities remain explicit diagnostics and are excluded from monetary projections.

Minute output has grain generation × UTC minute × merchant × currency × event type × application outcome. Refresh all buckets touched by the affected complete payment histories, aggregating neighbouring payments in those buckets again. Counts are replaced rather than incremented. The operational view uses applied events only for decision rates; zero-denominator rates are NULL, missing event counts are zero, and held, illegal, unknown-reference and identity-mismatch counts remain separate. Queries must select a generation and must not average percentages to roll up merchants or minutes.

Reference data is generated independently using the existing seed and arrival calendar, with a content hash and explicit arrival frontier. The command never calls the financial pipeline. Refresh is fenced against live writes and atomically reprojects every live generation, including old minutes. Seed changes and backwards frontiers are refused. For this small local MVP, one database-wide live-writer lock serialises live generations and reference changes; intake has its separate lock.

Reported Spark progress is persisted after completed sink commits, using a separate database connection from the callback. It includes source offsets, watermark and state-operator metrics. Status reads one PostgreSQL snapshot and checks both recorded frontiers, progress coverage of sink commits, immutable conflicts, reference holds and missing/unverified admitted events. Its consistency flag describes those recorded frontiers only: the broker head can advance, progress can lag a commit, and intake/live are not a distributed transaction. A missing late event keeps the flag false until a future controlled repair.

This slice proves the bounded fixture's duplicate/restart behaviour. It does not complete forced crash recovery, backfill parity, repeated eviction under sustained input, archival or latency/throughput measurement. Spark's [streaming guide](https://spark.apache.org/docs/4.2.1/streaming/apis-on-dataframes-and-datasets.html) describes the operator and callback semantics; [local evidence](../../evidence/stream-live-run.md) records what this implementation actually passed.
