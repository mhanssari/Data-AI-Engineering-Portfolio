# 0012: Bounded current-clock measurement

Accepted engineering default, 12 November 2026. No business-rule change.

Run three fresh isolated diagnostic topics, databases, checkpoints and JVMs against the same warmed local Kafka/PostgreSQL services. Each run publishes 100 warm-up payments over at least 20 seconds, waits for every warm-up event to be acknowledged and applied, then publishes 300 measured payments over at least 60 seconds. Each payment has two events: initiation and an authorisation decision (75% authorised, 25% declined), M001, GBP, 4,200 minor units. Pace five payments/second with a monotonic clock; never burst to catch up. Report actual offered rate and scheduling lag. These defaults define a small repeatable profile, not a capacity test.

The producer uses actual UTC event/ingestion/publish times and a newly declared dataset clock interval. One continuous live reader runs during production. Drain intake only after stopping live; this fits the laptop budget. Therefore the result covers the live path with one reader, not the simultaneous two-reader deployment or intake latency.

Use an independent autocommit database connection to poll applied events roughly once per second. The first query to see an applied event records PostgreSQL `clock_timestamp()` as its visibility observation; the event ledger, state and minute projection commit together. Join every observation to the producer's acknowledged partition/offset and, after intake, its archived broker LogAppendTime timestamp. Require one-to-one event/coordinate coverage, all 800 events retained/applied, 400 payments, expected decision totals and consistent recorded intake/live frontiers. Failed or missing samples fail the run; do not discard them. Exclude warm-up explicitly, calculate nearest-rank p50/p95 and maximum on all 600 measured events per run, and report each repeat separately.

The [metric catalogue](../metrics.md) owns definitions. This observer measures an upper bound on commit latency: commit precedes visibility, and polling adds delay. Record actual maximum observation gaps and clock round-trip brackets. All containers use the Docker Linux VM clock; check producer versus database time brackets and broker versus publication ordering (allowing broker millisecond precision). This is a clock sanity check, not an independent clock-calibration guarantee. Preserve per-event evidence, poll backlog and clock brackets in ignored local JSON. Do not use existing `first_commit_at`, `first_intake_at` or `ops.stream_batch.committed_at` for commit latency: their `now()` defaults are transaction-start timestamps. PostgreSQL documents the distinction between [`now()` and `clock_timestamp()`](https://www.postgresql.org/docs/18/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT).

Keep runtime transformations, migrations and financial rules unchanged. The producer/observer shares a small diagnostic container, so its polling and scheduling overhead are part of the measured environment. No timing gate is added to variable-speed CI runners. Small arithmetic regressions run in normal CI; the real profile remains an explicit local command. Report misses against the initial p95-under-15-second target honestly. Full-month historical replay, load sweeps, long soaks and cloud deployment are separate exercises.
